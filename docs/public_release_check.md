# 공개 전 점검 기록 (2026-10-22)

> 공개 저장소는 **이력을 버린 스냅샷**으로 만들었다(§3의 첫 번째 방법). 이 문서가 말하는 "이력"은 비공개 원본 저장소의 것이다.

저장소를 비공개에서 공개로 바꾸기 전에 개인정보·비밀값·저작권 문제가 될 만한 것을 훑은 기록이다. 점검 대상은 **추적하는 파일 93개(main)와 모든 브랜치의 git 이력**이다. 법률 자문이 아니라 규칙(`CLAUDE.md` 규칙 4, `docs/source_policy.md`)에 비춘 점검이며, 공개 여부는 소속 기관의 저작권·정보공개 담당 확인을 거쳐 정한다.

## 2. git 이력에 남아 있는 것

현재 파일에서는 고쳤지만 **이력(옛 커밋)에는 남아 있어** 공개하면 누구나 볼 수 있다.

- 국무원 영문판 문서의 **제목 1건**: `41bbc48`(출처 이용 조건 기록, 문서 안의 예시로 인용), `7af1f5d`(삭제한 커밋)
- 부서 대표 전화번호 2개: 위 커밋들과 `fa06298`, `bb315d7`, `6df95df`

위험이 작은 편이지만(제목 한 줄, 기관 공개 번호) `local_only_no_publish` 규칙의 취지와는 맞지 않는다.

## 3. 공개하는 방법 (선택)

| 방법 | 장단점 |
|---|---|
| **이력을 버린 새 저장소로 공개** (권장) | 현재 main 파일만 새 공개 저장소에 올린다. 이력 속 항목이 모두 사라진다. 대신 커밋·PR 이력이 공개 저장소에는 없다(비공개 원본은 그대로) |
| 이 저장소 이력을 고쳐 다시 쓰고 공개 | 이력은 남지만 B의 로컬 저장소와 열린 PR이 모두 어긋난다. 합의와 조율이 필요하다 |
| 이 저장소를 그대로 공개 | 가장 간단하지만 위 2번 항목이 노출된다 |

과제 제출에 **PR 주소**가 필요하다면 PR 이력은 지금 저장소에 있어야 한다. 그 경우 비공개 저장소를 평가자에게 초대하거나, 위 두 번째·세 번째 방법을 택한다.

## 4. GitHub Pages 배포

`docs/index.html`은 **합성 샘플**(`src/build_demo.py`)로 만든 데모 대시보드다. 제목·출처·주소·숫자를 모두 지어냈고 주소는 `sample.example`이다.

1. 저장소 설정 → Pages → Source: `main` 브랜치, 폴더 `/docs`
2. 주소: `https://<사용자>.github.io/policy-tech-trend-monitor/`
3. 비공개 저장소는 요금제에 따라 Pages가 안 될 수 있다(개인 무료 플랜은 공개 저장소만).

데모를 다시 만들려면 `python src/build_demo.py`(같은 입력이면 같은 결과).
